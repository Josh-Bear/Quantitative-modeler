# bl_lstm_views — ML-generated investor's views for Black-Litterman

Generates **Black-Litterman investor's views (the Q vector) automatically with machine
learning** instead of hand-set expert views, then runs the BL optimisation and backtests
it against SPY.

Adapted from the SET 2021–22 scholarship paper *"Black-Litterman Portfolio Management
Using Investor's View Generated by Recurrent Neural Networks and Support Vector
Regression"* (`BLmodel_views.pdf`), per the design in `BL_LSTM_Project_Summary.md`.

This is the **upstream view generator** that complements the repo's existing
`black_litterman_model/` web app (which does the BL math in JS). Here the views come from
a real LSTM+SVR pipeline; the resulting `output/views.json` is exported in the shape that
app's `BL.compute()` consumes.

## Pipeline

```
yfinance OHLCV (daily, 2010→)
      ↓
8 technical indicators           src/indicators.py  (pure pandas/numpy)
  MACD · RSI · squeeze_on · BB_width · KC_width · sq_momentum · OBV · Hilbert
      ↓  MinMax (train-only), 30-day windows, 5-day-ahead targets   src/preprocessing.py
LSTM (1 per stock, 8 outputs) → forecast all indicators 5 days ahead  src/lstm_model.py  (PyTorch)
      ↓                                          (Architecture B)
SVR: predicted indicators → predicted close price                  src/svr_model.py   (sklearn)
      ↓
view return q = (pred − last)/last → Q ;  Ω from test error        src/views.py
      ↓
Black-Litterman: Π, μ_BL, w*                                        src/black_litterman.py
      ↓
rolling 5-day-rebalance backtest vs SPY                            src/backtest.py
```

## Running

```bash
pip install -r requirements.txt        # numpy, pandas, scikit-learn, yfinance, torch
python run.py --quick                  # smoke test: 2 stocks, 3 epochs (~1–2 min)
python run.py                          # default: ~6 sector-spread stocks
python run.py --tickers AAPL,MSFT,NVDA,JPM
python run.py --full                   # paper scope: full DJI list, 400 epochs (SLOW — hours on CPU)
python run.py --device cpu             # force CPU (see GPU-memory note below)
python test.py                         # network-free BL-core sanity checks
```

### Notebook

`BL_LSTM_Portfolio.ipynb` walks the same pipeline step-by-step (fetch → indicators →
preprocess → train → SVR → BL → evaluate), calling the same `src/` modules. Open it from
the `bl_lstm_views/` folder so `from src import …` resolves:

```bash
jupyter notebook BL_LSTM_Portfolio.ipynb
```

Set `EPOCHS` (default 30) in the imports cell, or via env: `BL_EPOCHS=400 BL_DEVICE=cpu`.

#### Hyperparameter search

`Optuna_Hyperparameter_Search.ipynb` grid-searches the LSTM training knobs (learning rate ×
batch size × epochs = 27 combinations) per stock with Optuna's `GridSampler`, reusing the same
`src/` trainer (`_train_one`), and **reports** the validation MSE of every combination as a
sorted table + an `lr × batch` heatmap (`output/optuna_mse_map.png`). It does **not** apply
anything — read the tables, then set the values you want in `src/constants.py` by hand.

```bash
pip install optuna
jupyter notebook Optuna_Hyperparameter_Search.ipynb   # OPTUNA_SMOKE=1 (default): tiny epochs, minutes
OPTUNA_SMOKE=0 jupyter nbconvert --to notebook --execute --inplace \
    --ExecutePreprocessor.timeout=-1 Optuna_Hyperparameter_Search.ipynb   # real grid (200/400/600 epochs, hours)
```

Adapted from `Optuna_Hyperparameter_Search_Plan.md` (written for Keras + `data/processed/*.npz`)
to this repo's PyTorch + in-memory-dataset stack; deviations are listed in the notebook's intro.

**GPU memory.** On Apple Silicon the LSTM trains on the MPS GPU, which shares unified
memory with the whole system. If other apps are holding a lot of GPU memory you may hit
`MPS backend out of memory` — `run.py` catches this and **automatically falls back to CPU**.
You can also force it with `--device cpu`. Trained models are parked on the CPU and the GPU
cache is emptied between models, so residency stays at one model at a time.

Outputs land in `output/`: `views.json` (the BL view package), `report.txt` (the run
summary), `cache/` (downloaded prices), `models/`.

All knobs live in [`src/constants.py`](src/constants.py) — universe, the 8 features, LSTM
(`HIDDEN=60, LAYERS=4, DROPOUT=0.30, LR=5e-3, BATCH=256`), SVR (`RBF, C=5, ε=0.01`), BL
(`δ=2.5, τ=0.05, max-weight=10%`), and the 2010–2023 / 2024 / 2025 train/val/test splits.

## Design notes & honest caveats

This is a **correct, runnable research scaffold — not a guaranteed-profitable strategy.**
Backtest numbers are illustrative. Specifically:

- **No hardcoded fallback data.** Every other model in this repo ships a `constants.py`
  fallback so it runs offline; 14 years of daily OHLCV across the universe is far too large
  to inline. Instead `fetch_data.py` caches each ticker to `output/cache/*.csv` and falls
  back to that cache, so a *first* run needs network but repeats work offline. This is the
  one intentional departure from the repo convention.
- **Hilbert / HT_DCPERIOD** is a rolling-FFT dominant-cycle approximation (TA-Lib's exact
  transform needs the C library, which we deliberately avoid).
- **SVR is contemporaneous** (indicators(d) → close(d)); the whole 5-day horizon comes from
  the LSTM forecasting indicators 5 days ahead. SVR is just the indicators→price decoder.
- **View units.** Π and Σ are annualised, so per-horizon view returns are annualised
  *linearly* (×252/5) to share units; Ω is scaled by that factor squared. Linear (not
  compounded) annualisation avoids explosive Ω. Documented choice, not a standard.
- **MinMax on trending features** (OBV, band widths) can push val/test values outside [0,1];
  a known limitation of faithfully following the paper's scaling.

## What this is *not* (out of scope)

- It does not modify the JS web app to consume `views.json` live (it's exported for that).
- `--full` enables the paper scope but isn't run by default.
- No hyperparameter grid search (the grid-searched values from the paper are hardcoded).
